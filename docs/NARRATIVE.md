## 왜 · 어떤 아이디어로 · 어디로

**왜 만들었나.** 융합 수업을 설계하려면 "지금 이 교과의 이 성취기준과, 다른 교과의
무엇을 이으면 좋을까?"라는 질문에 답해야 합니다. 그런데 교육과정 문서는 교과별로
따로 존재해서, 교과의 경계를 **넘나드는 지도**가 없었습니다. 그 지도를 만들어보고
싶었습니다 — 성취기준을 점(node)으로, 교과를 잇는 융합의 실마리를 선(edge)으로 삼은
**하나의 그래프**로.

**어떤 아이디어로.** 두 가지 원칙을 지켰습니다.
- **"찾기"와 "판단"의 분리** — 후보는 임베딩 유사도로 결정적으로 좁히고(재현 가능),
  교육적 타당성만 AI가 판단합니다. 그래서 결과가 매번 흔들리지 않습니다.
- **"AI가 만들게 두지 않는다"** — AI에게 성취기준을 *번호로만* 참조하게 해서, 없는
  코드를 지어내는 할루시네이션을 구조적으로 막았습니다.
  (자세히 → [추출 알고리즘](#추출-알고리즘--사람을-위한-설명))

**어디로 (개선점).** 지금은 시작입니다. 생각하고 있는 방향은:
- 연결의 **커버리지 불균형** 해소 — 데이터가 얇은 학년군·교과(특히 1~2학년군)로 확장
- **candidate 11,088건**(그중 0.7대 4,008건)의 커뮤니티 검토를 통한 published 승격
- 사람이 신고한 **억지 연결**을 학습해 판정 기준을 정교화
- 임베딩·판정 모델을 **더 나은 것으로** 교체하며 재생성 (그래프는 모델과 함께 자랍니다)
- 표준 포맷(JSON-LD·CSV·그래프DB) export로 **재사용성** 확대
  (전체 목록 → [README의 로드맵](../README.md#로드맵))

## 추출 알고리즘 — 사람을 위한 설명

교과 간 연결은 어떻게 만들었을까요? 직관부터 이야기하겠습니다.

**문제.** "국어의 이 성취기준과 과학의 저 성취기준이 융합 수업으로 이어질까?"를
사람이 일일이 판단하면, 6,444개 성취기준의 조합은 **2,000만 쌍**이 넘습니다.
사람은 다 볼 수 없고, 그렇다고 AI에게 "교과 두 개 줄 테니 연결을 나열해"라고 하면
두 가지가 무너집니다 — ① 매번 답이 달라지고(재현 불가), ② **존재하지 않는 성취기준
코드를 지어냅니다**(할루시네이션).

**해법 — 찾는 일과 판단하는 일을 분리한다.** 마치 도서관에서 사서가 먼저 "주제가
비슷한 책"을 좁혀 오면(1단계), 전문가가 그중 진짜 쓸 만한 것을 고르는(2단계) 것과
같습니다.

- **1단계 — 후보 좁히기 (계산, 결정적).** 모든 성취기준을 의미 벡터(임베딩)로 바꾼
  뒤, 벡터가 서로 가까운(의미가 비슷한) 쌍만 추립니다. 순수 계산이라 **몇 번을
  돌려도 같은 결과**가 나오고, 여기서 나온 실제 유사도가 `semantic_score`입니다.
- **2단계 — 교육적으로 판단하기 (LLM).** 좁혀진 후보만 AI에게 보여주되, **성취기준을
  "1번, 2번" 같은 번호로만** 가리키게 합니다. AI는 코드를 *쓸 수 없고 고르기만* 하므로,
  없는 코드를 지어내는 일이 원천적으로 불가능합니다. AI는 이 연결이 교육적으로
  타당한지 판단해 품질 점수·연결 유형·융합 주제·수업 아이디어를 만듭니다.
- **게시 기준.** 그중 품질 점수 0.70 이상만 `published`로 올립니다. 양쪽 모두 산업수요 전문교과인
  연결은 서비스 대상(일반계 고등학교)에 맞지 않아 `candidate`에 둡니다.

핵심은 **"AI가 자유롭게 만들게 두지 않는다"** 입니다. 찾기는 계산에 맡겨 재현성을
확보하고, AI에게는 *좁혀진 선택지 안에서 고르고 설명하는* 역할만 줍니다. 이 구조가
할루시네이션을 막고 결과를 검증 가능하게 합니다.

실행 코드는 [`algorithm/`](./algorithm), 자세한 실행법은
[algorithm/README.md](./algorithm/README.md) 참고.

## AI 에이전트를 위한 작업 명세서

이 데이터셋을 **재현·확장**하려는 AI 에이전트(또는 자동화 파이프라인)를 위한 계약
수준의 명세입니다. 아래를 지키면 결과가 이 저장소의 `data/`와 동일한 규격으로
나옵니다.

### 0. 불변식 (INVARIANTS — 반드시 지킬 것)
- **INV-1 코드 무결성**: 출력 링크의 `source_code`·`target_code`는 반드시
  `data/standards.json`에 존재하는 **`key`** 여야 한다(같은 code가 두 과목에 쓰인 11건 때문에
  식별자는 `code`가 아니라 `key`다 — [SCHEMA](./SCHEMA.md)). **새 코드 생성 금지.**
- **INV-2 정규화**: 모든 링크는 `source_code < target_code`(유니코드 사전순)로 정렬.
- **INV-3 점수 범위**: `semantic_score`, `quality_score` ∈ [0, 1].
- **INV-4 결정성**: 1단계(후보 추출)는 동일 입력에 동일 출력을 낸다(무작위성 금지).
- **INV-5 검증 통과**: 산출물은 `node scripts/validate.mjs`를 오류 0으로 통과해야 한다.

### 1. 입력 (INPUT)
- `data/standards.json` — 성취기준 배열. 각 항목의 계약: `key`(string, 식별자), `code`(string, 원문 코드),
  `content`(string, 임베딩 대상 본문), `subject`/`subject_group`/`grade_group` 등 메타.
- **임베딩 캐시** — `{ "embeddings": { "<key>": number[] } }` 형태 JSON.
  각 벡터는 해당 `key`의 `content`를 임베딩한 것. 차원은 일관되어야 함(모델 자유).
  용량 문제로 리포에 미포함 → 에이전트가 생성. (원 데이터는 OpenAI 임베딩 사용)

### 2. 처리 단계 (PROCEDURE)

**Stage 1 — 후보쌍 추출 (결정적)**
1. 각 성취기준 벡터를 L2 정규화한다(코사인 = 내적).
2. 각 성취기준에 대해 다른 성취기준과의 코사인 유사도를 계산하고 **상위 top-k**
   (기본 `k=6`)를 남긴다.
3. 유사도 `< min-cos`(기본 0.45) 후보는 버린다.
4. 쌍을 INV-2로 정규화하고, **이미 존재하는 쌍**(`data/links.*.json`)은 제외한다.
5. 산출: `{ source_code, target_code, semantic_score }` 후보 목록.

**Stage 2 — LLM 판정 (코드 할루시네이션 차단 프로토콜)**
1. 후보를 배치(기본 25쌍)로 묶는다.
2. 프롬프트에 성취기준을 **번호(index)로만** 제시한다. 예: `1. <content A>` /
   `2. <content B>`. 모델에게 코드 문자열을 절대 노출·요구하지 않는다.
3. 모델은 각 후보에 대해 다음 스키마의 JSON을 **인덱스로 참조**해 반환한다:
   ```jsonc
   { "pair": [1, 2], "valid": true, "link_type": "cross_subject",
     "quality_score": 0.85, "rationale": "...", "integration_theme": "...",
     "lesson_hook": "..." }
   ```
4. **응답 검증·폐기 규칙**: `link_type`이 허용 집합
   (`cross_subject|same_concept|application|prerequisite|extension`)이 아니거나,
   `quality_score`가 범위를 벗어나거나, `pair` 인덱스가 배치 범위를 벗어나면 **그 판정은
   폐기**한다(재시도 가능). 모델이 만든 코드 문자열은 **무시**하고, 인덱스로 원본
   코드를 역참조해 채운다(INV-1 보장).
5. 산출: 원본 코드로 복원한 링크 레코드.

**Stage 3 — 게시 정책 (선택)**
- `quality_score ≥ 0.70` → `published`, 그 미만 → `candidate`.
- 임계값은 정책 파라미터이며 `algorithm/promote-links.mjs`로 사후 조정 가능.

### 3. 출력 (OUTPUT 계약)
[`docs/SCHEMA.md`](./SCHEMA.md)의 링크 필드 규격을 따른다. 필수:
`source_code, target_code, link_type, rationale, integration_theme, lesson_hook,
semantic_score, quality_score, generation_method`.

### 4. 파라미터 (기본값)
| 이름 | 기본 | 의미 |
|------|------|------|
| `top-k` | 6 | 성취기준당 후보 수 |
| `min-cos` | 0.45 | 후보 최소 코사인 |
| `batch-size` | 25 | 배치당 후보 쌍 수 |
| `concurrency` | 3 | 동시 판정 배치 수 |
| 게시 임계 | 0.70 | published 승격 하한 |

### 5. 확장 지침 (AGENT DIRECTIVES)
- **모델 교체 시**: 2단계 판정 모델을 바꿔도 위 프로토콜(인덱스 참조·검증·폐기)은
  그대로 유지한다. 코드 노출 금지 규칙을 완화하지 말 것.
- **임베딩 교체 시**: 벡터 차원만 일관되면 무방. 교체 후 `semantic_score` 분포가
  달라지므로 `min-cos`를 재보정한다.
- **대량 생성 후**: 반드시 `scripts/validate.mjs`로 참조 무결성(dangling)·정규화·점수
  범위를 확인하고, 실패 시 게시하지 않는다(INV-5).
- **품질 보고**: 커버리지·기각률·게시 비율을 함께 남겨, 무엇이 누락됐는지 은폐하지
  않는다.

## 재현하고 더 잘 만들고 싶은 분들께 — 팁

명세서가 "무엇을"이라면, 이건 작업하며 배운 "실전 감각"입니다.

- **품질의 8할은 임베딩에서 갈립니다.** 성취기준 `content`는 짧아서, 본문만 임베딩하면
  표면적 유사도에 치우칩니다. `content`에 `explanation`·`keywords`를 덧붙여 임베딩하면
  recall이 눈에 띄게 좋아집니다. 한국어 특화 임베딩 모델도 시도해볼 만합니다.
- **`min-cos`는 하나로 고정하지 마세요.** 교과군을 *넘는* 융합(교차군)은 유사도가
  낮게 나오고, *같은* 교과군 내 계열성은 높게 나옵니다. 단일 임계값보다 **교과쌍
  성격에 따른 적응형 임계값**이 더 좋은 후보를 남깁니다.
- **"작위적 융합"을 경계하세요.** 둘 다 '환경'을 언급한다고 이어버리면 억지 연결이
  됩니다. 판정 프롬프트에서 *"이 둘을 한 수업으로 어떻게 잇는가"* 를 반드시 쓰게 하면,
  설명이 안 되는 표면 유사 연결이 걸러집니다. `lesson_hook`이 억지스러우면 그 연결도
  의심하세요.
- **방향이 있는 연결은 방향을 지키세요.** `prerequisite`(선수)·`extension`(확장)은
  순서가 의미입니다. 저장은 `source < target`로 정규화하되, **방향은 `link_type`으로**
  보존해야 "무엇이 무엇의 선수학습인지"가 남습니다.
- **검증을 사람 눈이 아니라 CI에 맡기세요.** `scripts/validate.mjs`를 PR 게이트로 걸면,
  참조가 깨진 링크(dangling)나 정규화 위반이 병합되는 사고를 원천 차단합니다.
  (실제로 이 데이터도 성취기준 버전이 어긋나 링크 500여 건이 깨졌던 걸 이 검증이
  잡아냈습니다.)
- **더 잘 만드는 지름길은 "사람의 판단을 되먹이는 것"입니다.** 커뮤니티가 신고한 억지
  연결과 승격/강등 이력은 그 자체로 훌륭한 학습 신호입니다. 이 신호로 판정 기준을
  조정하면, 모델을 키우지 않고도 그래프가 좋아집니다.
